Manual das Skills

O PIV Loop

Plan → Implement → Verify. Oito skills que levam uma ideia da página em branco até um pull request que um humano pode aprovar — um passo deliberado por vez.

O que é o PIV loop

PIV significa plan → implement → verify. É o formato pelo qual as skills deste projeto conduzem o trabalho.

  • Plan transforma uma ideia em um intent, uma arquitetura e um conjunto de tickets.
  • Implement constrói um ticket na própria branch e escreve um implementation report.
  • Verify tenta provar que a mudança está errada antes que ela vá para produção: um review escreve as findings, uma rodada de triagem resolve cada uma, e só então o trabalho é commitado e entregue a um humano.

Duas propriedades sustentam o conjunto. Cada passo lê o artifact que o passo anterior escreveu — os reports não são burocracia, são o input. E cada passo é iniciado por você, nunca pelo passo anterior.

A ideia central

Nada se encadeia sozinho. Cada skill termina dizendo qual é o próximo movimento; você decide se o executa. É isso que impede um plano ruim de virar um PR mergeado enquanto você estava longe.

A chain em um relance

Plan
piv-create-prd ou / e piv-create-architecture → piv-create-tickets
Implement
piv-implement-ticket
Verify
piv-review-changes → piv-fix-findings → piv-commit-changes → piv-create-pr

O loop fecha em um PASS. piv-fix-findings sempre devolve para um piv-review-changes novo. Só um veredito PASS conquista um commit.

Leia as setas como "este é o próximo movimento oferecido", não como automação. As três skills de verify antes do PR são o gate; o PR em si é a entrega para fora do loop, para um humano que revisa, aprova e faz o merge.

Por onde começar?

Raramente você precisa das oito. Encontre a linha que corresponde ao que você tem em mãos.

O que você temComece porPor quê
Uma ideia de produto, nada escrito piv-create-prd Você precisa fixar o o quê e por quê antes que alguém discuta o como.
Um PRD ou um epic, com incerteza técnica real piv-create-architecture Decidir a abordagem deliberadamente, em vez de deixar os tickets a codificarem por acidente.
Um intent claro, com pouco risco técnico piv-create-tickets Um atalho legítimo — só saiba que você pulou a etapa de arquitetura de propósito.
Um ticket id pronto para construir piv-implement-ticket Tickets carregam o próprio contexto, então o loop pega um do zero só pelo id.
Trabalho construído numa branch, ainda não commitado piv-review-changes Este é o gate que decide se a mudança conquista um commit.
Um review report com findings piv-fix-findings Findings são input, não ordem de serviço — você decide sobre cada uma.
Um veredito PASS piv-commit-changes Commits atômicos e, depois, o PR.

Plan

A etapa de plan produz três tipos de documento, em ordem crescente de concretude: intent (o PRD), decisões (o architecture doc) e unidades de trabalho (os tickets). São skills separadas porque respondem a perguntas diferentes, e misturá-las é como um PRD silenciosamente vira uma spec.

Plan · passo 1

piv-create-prd

Entrevista você para fixar o problema, o porquê de construí-lo e uma hipótese falseável — e então escreve um PRD em nível de produto. Só intent: o quê e por quê, nunca decisões de engenharia.

Input
[ideia de produto] e, opcionalmente, caminhos para research docs — entrevistas com usuários, temas de tickets de suporte, analytics, análises de concorrentes. Em branco, começa pelas perguntas.
Output
docs/.plans/<intent-slug>.prd.md — problem statement, evidências, tese, hipótese, usuário-alvo e JTBD, MVP, métricas de sucesso, não-objetivos, questões em aberto.
Como roda
Uma entrevista agrupada em cinco fases, cada uma terminando em um gate onde ela espera por você.
Guards
  • Evidence-or-TBD — todo requisito rastreia até algo que você disse ou que um doc mostrou; o que é desconhecido é escrito como "TBD — needs validation".
  • Intent-framed, não solution-prescriptive — se só uma solução couber no problem statement, aquilo é uma spec, não um PRD.
Próximo passo
piv-create-architecture para decidir o como, ou piv-create-tickets direto quando o trabalho for tecnicamente trivial.
Use quando
  • Você está começando algo greenfield e ninguém escreveu o problema ainda.
  • Você está dimensionando um novo epic num produto existente — o epic vira o input.
  • Duas pessoas do time descreveriam "o problema" de formas diferentes.
Pule quando o intent já existir como um epic ou brief escrito em que você confia.
Plan · passo 2

piv-create-architecture

Pesa as opções de como construir um intent, recomenda uma direção e escreve um architecture decision doc — abordagem, building blocks, modelo de dados, riscos. Ela para no nível da decisão; não é um plano de implementação.

Input
O caminho de um PRD, um epic, um brief ou uma ideia em formato livre, mais reference docs opcionais. Referências externas (URL, page key, ticket id) são buscadas na origem primeiro.
Output
docs/.plans/<intent-slug>.architecture.md — problema e objetivos, abordagens consideradas, abordagem recomendada, decisões-chave, peças faltantes, spikes e experimentos, questões em aberto.
Como roda
Modo grilling. Ela contesta suas premissas em vez de transcrevê-las, e sinaliza as portas de mão única que merecem um spike antes do compromisso.
Próximo passo
piv-create-tickets <caminho do intent> docs/.plans/<intent-slug>.architecture.md — ou construir antes um spike que esteja bloqueando.
Use quando
  • Existe mais de uma forma plausível de construir a coisa.
  • Uma decisão é difícil de reverter depois — formato de armazenamento, fronteira de serviço, um fornecedor.
  • O trabalho toca uma parte desconhecida do sistema.
Pule quando a abordagem for óbvia e a mudança for local. Diga em voz alta que você pulou.
Plan · passo 3

piv-create-tickets

Decompõe um intent em tickets do tamanho de um agent, com acceptance criteria e um grafo de dependências, e então os cria no tracker do projeto. É também aqui que o epic nasce: ela cria o epic e publica nele o PRD e o architecture doc antes de qualquer ticket existir — as duas plan skills anteriores escrevem arquivos locais e não sabem nada sobre tracker.

Input
Um intent — PRD, epic, path, URL ou ticket id — opcionalmente com o architecture doc dele.
Output
O epic, com o PRD e o architecture doc publicados nele — e tickets reais embaixo dele, cada um com descrição, escopo, contexto próprio, depends on e acceptance criteria. Todo ticket referencia o epic de volta, para que o rastro sobreviva.
Como roda
Não interativa durante a decomposição e o mapeamento de dependências, e então um gate onde você confirma a divisão antes que qualquer coisa seja criada.
Guard
Sem architecture doc, ela avisa, mantém os tickets no formato de resultado em vez de implementação, e oferece piv-create-architecture primeiro quando a incerteza técnica é real.
Próximo passo
piv-implement-ticket <ticket-id> — ou iniciar em paralelo uma leva de tickets independentes.
Use quando um intent estiver resolvido e você precisar fatiá-lo em unidades que um agent consiga terminar e comprovar. Cada ticket carrega o próprio contexto, então pode ser pego do zero.

Implement

Implement

piv-implement-ticket

Constrói um ticket, task por task, na própria branch, validando a cada passo, e escreve um implementation report.

Input
<ticket-id | caminho-do-plan-document>. Em branco, ela pergunta qual ticket.
Output
docs/.reports/<ticket-id>-report.md — resumo, tasks concluídas, testes adicionados, resultados de validação, desvios em relação ao ticket, problemas encontrados. O status é COMPLETE ou PARTIAL.
Como roda
Resolver o ticket → trabalhar em uma branch → ler o ticket de ponta a ponta → drift check → executar as tasks em ordem → fechar a estratégia de testes → rodar as checks → verificação final.
Próximo passo
piv-review-changes, em uma sessão própria, recebendo o ticket id.
Por que os desvios importam. O reviewer lê este report. Um desvio registrado aqui é uma decisão intencional que o reviewer não deve apontar; o mesmo desvio não escrito volta como uma finding.

Verify

Verify são quatro skills e uma regra: review e fixes são rodadas separadas. O reviewer escreve findings e não toca em código. A rodada de triagem decide o que acontece com cada uma, com você decidindo a divisão.

Verify · o gate

piv-review-changes

Revisa a mudança pronta em busca de bugs, defeitos de segurança e violações de padrões, e escreve um review report. É um report, nunca uma edição.

Input
[ticket id] — em branco, é extraído do nome da branch.
Output
docs/.reports/<ticket-id>-review.md — escopo (todo arquivo lido), findings agrupadas em critical / high / medium / low, e as checks executadas. Cada finding carrega evidência, impacto e um fix concreto.
Veredito
CHANGES REQUESTED quando qualquer finding critical ou high sobrevive. PASS caso contrário — um PASS com findings medium e low é normal.
Como roda
Resolver a mudança → resolver as deferrals anteriores → ler os padrões que a mudança precisa cumprir → ler cada arquivo alterado de ponta a ponta → montar o caso → aplicar três filtros que eliminam findings não comprovadas.
Próximo passo
PASS → piv-commit-changes. CHANGES REQUESTED → piv-fix-findings, recebendo o caminho deste report.
Use antes de commitar qualquer coisa, e de novo depois de cada rodada de fix. Em um re-review, ela sobrescreve o report anterior: ele é o estado atual da branch, e as decisões sobre findings antigas vivem no tracker, não ali.
Verify · triagem

piv-fix-findings

Tria as findings do review, corrige uma a uma as que você escolher, com testes, adia e registra as demais no tracker, valida e escreve um fix report.

Input
[caminho do review report] — em branco, usa o review escrito para esta branch.
Output
docs/.reports/<ticket-id>-fixes.md — Fixed, Deferred (com as referências das issues), Needs a human look, Noise / won't-fix, e as checks executadas.
Como roda
Triar cada finding em um dos quatro grupos → corrigir o conjunto fix now uma de cada vez, cada uma com um teste que a comprove → validar a branch inteira.
Próximo passo
piv-review-changes de novo, em uma sessão nova, recebendo o ticket id.
Por que o report existe. A triagem é uma decisão humana, e uma decisão que vive só na conversa desaparece na próxima rodada. O fix report e as issues de deferral são o que dizem ao re-review que uma finding já foi resolvida — assim o que foi decidido permanece decidido.
Verify · commit

piv-commit-changes

Commita o trabalho pronto como commits atômicos e convencionalmente tagueados — cada um uma unidade coerente de trabalho que a subject line consiga nomear.

Input
[ticket id] — em branco, é extraído do nome da branch.
Output
Commits na branch, mais um resumo "What Changed" para quem for percorrer o git log. A rodada termina com a árvore limpa.
Como roda
Conferir onde você está → inspecionar a árvore → agrupar as mudanças → commitar cada grupo → acrescentar um body quando a subject não bastar.
Próximo passo
piv-create-pr. O ticket id viaja no nome da branch, e é de lá que a próxima skill o lê.
Use quando o veredito do review for PASS. Normalmente isso é um único commit; quando a árvore contém trabalho não relacionado, ela divide, e qualquer coisa que não caiba em nenhum grupo interrompe a rodada e pergunta a você.
Verify · entrega

piv-create-pr

Abre o pull request da branch finalizada e entrega a URL a um reviewer humano.

Input
[base branch] — em branco, usa a base branch do projeto.
Output
Uma branch publicada e um review request aberto: resumo, o que mudou, validação, notas para o reviewer, questões em aberto, ticket vinculado. Ela reporta o número do PR, a URL e as branches base ← head.
Como roda
Resolver a base branch → conferir se a branch está entregável → reunir o body a partir dos reports → publicar → abrir o review request.
Próximo passo
Um humano revisa, aprova e faz o merge. O loop do agent termina no merge.
Portável por design. Um pull request no GitHub, um merge request no GitLab, ou marcar uma branch como pronta para review em outro lugar — ela usa o ferramental que o repo já usa.

Artifacts e onde eles vivem

Cada passo lê o artifact anterior, então os caminhos importam. Eles são definidos em docs/ISSUE-TRACKER.md.

docs/ISSUE-TRACKER.md é seu para customizar — é onde um projeto declara qual tracker usa e quais são os caminhos dos artifacts, e as skills leem esse nome de arquivo e nenhum outro. A pasta docs/ traz exemplos prontos para copiar por cima dele: ISSUE-TRACKER-gitlab.md, ISSUE-TRACKER-jira.md e ISSUE-TRACKER-md.md, para um projeto que mantém os tickets em arquivos markdown locais.

Os plans são escritos localmente e continuam lá; piv-create-tickets publica uma cópia no epic — um comentário no GitHub, um attachment no GitLab e no Jira — para que as decisões viajem com o trabalho em vez de ficarem na máquina que as escreveu.
O intent-slug

Todo artifact de um mesmo intent carrega o mesmo intent-slug: o kebab-slug do título do epic ou do produto. Todo artifact abre com um header block — uma lista markdown curta, um campo em negrito por linha — e o slug é o primeiro campo dela. Os passos seguintes leem o slug do artifact em vez de derivá-lo de novo — assim, um PRD escrito como user-auth.prd.md nunca ganha um authentication.architecture.md ao lado.

Quando o trabalho não tem ticket, o intent-slug ocupa o lugar do ticket id nos nomes dos reports.

House rules

  1. Nada se encadeia sozinho. Cada skill termina oferecendo o próximo movimento; você o executa.
  2. Cada passo lê o artifact anterior. Reports são o input com que a próxima rodada trabalha, não burocracia.
  3. Skills param em vez de adivinhar. Nenhum tracker escolhido, um ticket id ambíguo, uma árvore suja com trabalho que não cabe em nenhum grupo, um review report que não existe — a rodada para e pergunta.
  4. Review e fixes são rodadas separadas. O reviewer escreve as findings e não toca em código; a rodada de triagem decide o que acontece com cada uma, com você decidindo a divisão.
  5. O loop fecha em um PASS. Uma rodada de fix sempre devolve para um review novo, que lê as issues de deferral para que o que foi decidido permaneça decidido.
Se uma rodada parar e perguntar algo

Isso é o design, não uma falha. Responda e rode de novo — adivinhar é a única coisa que estas skills não farão por você.

Um percurso completo

Um epic, do início ao merge. Cada linha é algo que você digita; cada rodada acontece em uma sessão própria.

  1. piv-create-prd — a entrevista e, ao final, um PRD em docs/.plans/team-inbox.prd.md.
  2. piv-create-architecture docs/.plans/team-inbox.prd.md — o grilling e, ao final, um decision doc ao lado.
  3. piv-create-tickets docs/.plans/team-inbox.prd.md docs/.plans/team-inbox.architecture.md — confirme a divisão no gate; os tickets vão para o tracker.
  4. piv-implement-ticket 123 — uma branch, as tasks, os testes e docs/.reports/123-report.md.
  5. piv-review-changes 123 — veredito CHANGES REQUESTED, 1 high e 3 medium em docs/.reports/123-review.md.
  6. piv-fix-findings docs/.reports/123-review.md — você corrige a high e uma medium, adia duas no tracker; docs/.reports/123-fixes.md registra cada decisão.
  7. piv-review-changes 123 — ela lê as issues de deferral, e o veredito é PASS.
  8. piv-commit-changes 123 — commits atômicos, árvore limpa.
  9. piv-create-pr — o PR abre e a URL vai para um humano.

Os passos 5–7 se repetem quantas vezes a branch precisar. Esse ciclo é o loop.

Solução de problemas

O review insiste em levantar algo que eu já decidi adiar.

O adiamento precisa existir como uma issue no tracker, não só como uma linha na conversa. piv-fix-findings abre essas issues; piv-review-changes as lê no passo 2 dele. Se a issue não estiver lá, a finding volta com razão.

O reviewer apontou algo que eu mudei de propósito.

Registre em Deviations from the ticket no implementation report. Essa seção é o sinal de intenção para o reviewer.

Posso pular o PRD ou o architecture doc?

Pode, e as duas skills vão dizer isso em voz alta em vez de fingir o contrário. Pular o architecture doc num trabalho com incerteza técnica real é o caro dos dois — os tickets acabam codificando decisões que ninguém tomou.

Posso rodar vários tickets ao mesmo tempo?

Pode. piv-create-tickets mapeia as dependências no passo 4 justamente para que você veja quais tickets formam uma leva independente.

Nada aconteceu depois que uma skill terminou.

Esperado. Skills não se encadeiam — leia o próximo movimento que ela ofereceu e execute-o você mesmo.
