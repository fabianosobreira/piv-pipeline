Manual das Skills

O PIV Loop

Plan → Implement → Verify. Dez skills que levam uma ideia da página em branco até um pull request que um humano pode aprovar — um passo deliberado por vez, na sua máquina, com o GitHub como único remote.

O que é o PIV loop

PIV significa plan → implement → verify. É o formato pelo qual as skills deste projeto conduzem o trabalho.

  • Plan transforma uma ideia em um spec, audita esse spec contra o seu código e as issues e PRs do GitHub, corta-o em um ticket por task e o publica como uma única issue do GitHub.
  • Implement constrói uma task por vez na branch do intent e escreve um implementation report.
  • Verify tenta provar que cada task está errada antes do commit: um review escreve as findings, uma rodada de triagem resolve cada uma, e só então a task é commitada. Com todas as tasks commitadas, o PR abre e é auditado contra o spec antes que um humano faça o merge.

Duas propriedades sustentam o conjunto. Cada passo lê o artifact que o passo anterior escreveu — os reports não são burocracia, são o input. E cada passo é iniciado por você, nunca pelo passo anterior.

A ideia central

Nada se encadeia sozinho. Cada skill termina dizendo qual é o próximo movimento; você decide se o executa. É isso que impede um plano ruim de virar um PR mergeado enquanto você estava longe.

A chain em um relance

Plan
piv-spec → piv-review-spec → piv-slice
Implement
piv-implement

Uma task por vez. Implement, review, fix e commit se repetem para cada task do epic, na ordem dele.

Verify
piv-review → piv-fix → piv-commit → piv-open-pr → piv-review-pr

Cada task fecha em um PASS. piv-fix sempre devolve para um piv-review novo. Só um veredito PASS conquista um commit; o PR abre quando todas as tasks estão commitadas.

Leia as setas como "este é o próximo movimento oferecido", não como automação. Review, triagem e commit são o gate de cada task; o PR é a entrega para fora do loop, para um humano que revisa, aprova e faz o merge.

Raramente você precisa das dez. Encontre a linha que corresponde ao que você tem em mãos.

Setup

O setup não é um passo do loop: roda uma vez por projeto, antes do primeiro passo, e de novo sempre que chegar uma versão mais nova das skills.

Instale as skills a partir da raiz do seu projeto com um único comando. Ele exige Node.js e git, em Windows com Git Bash, macOS ou Linux, e instala só para o Claude Code. Depois, rode /piv-setup.

npx skills@1.7.2 add fabianosobreira/piv-pipeline#releases -s '*' -a claude-code --copy -y
  • Faça o commit do lock file junto com as skills. O comando cria o skills-lock.json na raiz do projeto; faça o commit dele junto com o .claude/skills/.
  • Não ponha arquivos seus nas pastas piv-*. Cada pasta .claude/skills/piv-*/ é substituída inteira a cada execução, então um arquivo que você acrescentar ali é apagado.
  • Uma instalação que falhou se recupera rodando o comando de novo.
  • Para atualizar, rode o mesmo comando de novo. Ele não fixa versão: instala o estado atual da branch releases, e o lock file registra só o hash instalado. Para fixar uma versão à mão, troque #releases por #vX.Y.Z.
Setup · uma vez por projeto

piv-setup

Confere que o projeto está no GitHub com o gh autenticado, instala no docs/ do projeto os docs que todo passo lê, incorpora ao docs/git-conventions.md as regras de git que o projeto já tem — as suas regras vencem os defaults que vêm com a skill — e faz o git ignorar o .piv/.

Input
Nenhum.
Output
docs/piv-loop.md; docs/git-conventions.md; e a linha .piv/ no .gitignore da raiz, criado quando não existe. Depois, um commit, se você aprovar.
Como roda
Conferir o remote e o gh, investigar os docs existentes e o harness → rascunhar o docs/git-conventions.md → apresentar o plano inteiro em um único gate → instalar → mostrar a mensagem de commit e esperar por você.
Guards
  • GitHub ou nada — um origin fora do github.com, ou o gh sem login, encerra a rodada com o comando que resolve.
  • O harness vence — regras de git de CLAUDE.md, AGENTS.md, arquivos de regras e tooling de commit prevalecem sobre o git-conventions.md que vem com a skill; cada uma guarda a nota de onde veio.
  • As necessidades das skills são conferidas — base branch, formato do commit subject, formato do PR title e as commit tags são obrigatórios; uma regra que quebre um deles volta para você. Branch name ou subject sem o número da issue são permitidos, ao custo de as skills pedirem a issue a cada rodada.
  • Nada é sobrescrito em silêncio — um .gitignore existente só ganha a linha .piv/.
Próximo passo
Nenhum no loop: termina no commit. Escolha o ponto de partida em Por onde começar?
Use
  • Logo depois de instalar as skills num repo com o comando acima.
  • Quando suas regras de git vivem em CLAUDE.md ou AGENTS.md — ela pode movê-las para o docs/git-conventions.md e deixar um ponteiro no lugar, se você aceitar.
  • Quando chegar uma versão mais nova das skills e os docs precisarem acompanhar.

Plan

A etapa de plan produz o spec, que fixa requisitos, design, tasks e verificação em um só arquivo; a review dele, que o confere contra o que já existe; e os tickets, cada um uma fatia literal do spec para uma task, acompanhados por um epic local e publicados como uma única issue do GitHub. São skills separadas porque respondem a perguntas diferentes. O piv-write-prd fica à parte: o PRD dela é uma entrada comum do piv-spec, passada pelo caminho.

Plan · passo 1

piv-spec

Entrevista você em fases fixas e então escreve um spec de 10 seções. Toda afirmação vem de uma resposta sua; o agent nunca preenche uma lacuna.

Entrada
[intent-slug] e o conceito — um parágrafo, um arquivo ou um documento completo com links. As URLs que você passar são lidas sem perguntar; links que ela encontrar sozinha são perguntados antes. Um PRD é um desses documentos: passe o caminho dele, .piv/[intent-slug]/prd.md, e a pasta é reaproveitada. Em branco, começa com perguntas.
Saída
.piv/[intent-slug]/spec.md — objetivo, non-goals, requisitos funcionais (FR), não funcionais (NFR), acceptance criteria (AC), restrições (C), design (D), plano de tasks (T), comandos de verificação, limites e um decision log. Intent-slug e Language ficam no cabeçalho.
Como roda
Oito fases de perguntas numeradas; todo statement remete a uma resposta sua. Um validador incluso checa estrutura e rastreabilidade: todo NFR, C e D precisa ser citado por uma task, e toda referência precisa resolver. Status: ready assim que o lint fica limpo.
Próximo passo
piv-review-spec [intent-slug], em uma sessão própria.
Use quando
  • Você tem uma mudança em mente, com ou sem PRD, e quer fixá-la antes que alguém construa.
  • Um AI agent vai implementá-la e precisa de requisitos que consiga verificar.
Pule quando a mudança for uma correção de uma linha que você mesmo faz à mão.
Plan · passo 2

piv-review-spec

Audita um spec pronto antes que ele seja publicado: o que o código já tem, o que as issues e PRs do repo já dizem, e cada item que a entrevista deixou adiado. Resolve cada um com você e marca a revisão do spec como reviewed.

Entrada
[intent-slug], para um spec com Status: ready. Um draft encerra a execução.
Saída
O spec, editado só com as suas respostas, em Status: reviewed; e .piv/[intent-slug]/spec.review.md — o que existe no código, as issues e PRs em conflito, o que você resolveu, o que mudou, e o Reviewed-hash do spec. Um problema que pede uma entrevista nova reabre o spec como draft.
Como roda
Ler o spec → buscar no código → buscar nas issues e PRs do repo com o gh, só leitura → perguntar, no mesmo formato numerado do piv-spec → aplicar as respostas e rodar o lint → marcar o resultado. Sem o gh autenticado ela para, a menos que você decida seguir sem a checagem remota.
Próximo passo
piv-slice [intent-slug], em uma sessão própria.
Por que uma rodada separada. A entrevista que escreveu o spec é a pior juíza dele. Uma sessão nova encontra o código que já faz metade do trabalho, e a issue fechada que já rejeitou a ideia, antes que o spec vire uma issue pública.
Plan · passo 3

piv-slice

Corta um spec revisado em um ticket por task e um epic que os acompanha, e então publica o spec como a única issue do GitHub do intent. Cada ticket copia, linha por linha, a parte do spec de que sua task precisa — nada é criado nem reescrito.

Entrada
[intent-slug], para um spec em Status: reviewed cujo hash bate com a review. Um draft, um ready, ou um spec editado depois da review encerra a execução.
Saída
tasks/T-xx/T-xx.md, um ticket por task, cada um com um header block (Spec com o hash da revisão, Slice, Type, Blocked by, Size, Intent-slug, Language) e as seções do spec; epic.md, a lista de tasks; e uma issue do GitHub, com o spec inteiro no body, um label de tipo — bug, feature ou task — e você como assignee.
Como roda
Sem interação durante o corte, o lint e o preflight do gh, e então um gate em que você aprova a issue: o título, o label, e o aviso de que o spec será publicado por inteiro. Um validador incluso, o lint_ticket.sh, rejeita toda linha de ticket que não seja uma linha literal do spec, e todo ticket com mais de uma task; nada chega ao GitHub até todos os tickets passarem.
Próximo passo
piv-implement [#N], em uma sessão própria.
Use quando um spec estiver revisado e você precisar fatiá-lo em unidades que um agent consiga terminar e comprovar, uma de cada vez.
Avulsa

piv-write-prd

Entrevista você para fixar o problema, o porquê de construí-lo e uma hipótese falseável — e então escreve um PRD em nível de produto. Só intent: o quê e por quê, nunca decisões de engenharia. Não é um passo do loop: o PRD dela é uma entrada comum do piv-spec, passada pelo caminho.

Input
[ideia de produto] e, opcionalmente, caminhos para research docs — entrevistas com usuários, temas de tickets de suporte, analytics, análises de concorrentes. Em branco, começa pelas perguntas.
Output
.piv/[intent-slug]/prd.md — problem statement, evidências, tese, hipótese, usuário-alvo e JTBD, restrições, MVP, métricas de sucesso, não-objetivos, questões em aberto.
Como roda
Uma entrevista agrupada em cinco fases, cada uma terminando em um gate onde ela espera por você. As perguntas são numeradas ao longo de toda a rodada, e a hipótese volta para você, montada com as suas próprias palavras, antes de ser fechada.
Guards
  • Evidence-or-TBD — todo requisito rastreia até algo que você disse ou que um doc mostrou; o que é desconhecido é escrito como "TBD — needs validation".
  • Intent-framed, não solution-prescriptive — se só uma solução couber no problem statement, aquilo é uma spec, não um PRD.
Próximo passo
piv-spec .piv/[intent-slug]/prd.md, em uma sessão própria.
Use quando
  • Você está começando algo greenfield e ninguém escreveu o problema ainda.
  • Você está dimensionando um trabalho novo num produto existente — o research doc, o decision plan ou os docs do produto que trazem o contexto viram o input.
  • Duas pessoas do time descreveriam "o problema" de formas diferentes.
Pule quando a mudança já estiver clara o bastante para ir direto ao piv-spec.

Implement

Implement · por task

piv-implement

Constrói uma task a partir do ticket dela, na branch do intent, validando a cada passo, e escreve um implementation report. O trabalho fica sem commit para o review.

Input
[#N | intent-slug] [T-xx]. Em branco, pega a issue do nome da branch e a próxima task do epic: a que está em andamento, ou a primeira cujas dependências estão todas commitadas.
Output
tasks/T-xx/T-xx.report.md — resumo, tasks concluídas, testes adicionados, resultados de validação, desvios em relação ao ticket, problemas encontrados. O status é COMPLETE ou PARTIAL — PARTIAL também quando um arquivo alterado é ignorado pelo git, porque ele nunca viaja com a branch. A task vira [~] no epic.
Como roda
Resolver a task e conferir as dependências → trabalhar na branch do intent, criada pela primeira task como [tag]/[N]-[intent-slug] → ler o ticket de ponta a ponta e checar o drift → executar as tasks em ordem → fechar a estratégia de testes → rodar as checks → verificação final.
Próximo passo
piv-review [#N] [T-xx], em uma sessão própria.
Por que os desvios importam. O reviewer lê este report. Um desvio registrado aqui é uma decisão intencional que o reviewer não deve apontar; o mesmo desvio não escrito volta como uma finding. A exceção é um teste: um teste desabilitado, afrouxado, reescrito ou removido continua bloqueando o review, mesmo quando um desvio o explica.

Verify

Verify são cinco skills e uma regra: review e fixes são rodadas separadas. O reviewer escreve findings e não toca em código. A rodada de triagem decide o que acontece com cada uma, com você decidindo a divisão. Review, triagem e commit rodam por task; o PR e a auditoria dele rodam uma vez, para o intent inteiro.

Verify · o gate, por task

piv-review

Revisa a mudança sem commit de uma task em busca de bugs, defeitos de segurança e violações de padrões, e escreve um review report. É um report, nunca uma edição.

Input
[#N | intent-slug] [T-xx] — em branco, pega a issue do nome da branch e a task em andamento do epic.
Output
tasks/T-xx/T-xx.review.md — escopo (todo arquivo lido), findings agrupadas em blocking / critical / high / medium / low, e as checks executadas, entre elas a suíte de testes completa. Uma finding blocking é um teste vermelho, faltando ou enfraquecido, ou uma behavior sem teste — um fato, fora da escala de severidade. Cada finding carrega evidência, impacto e um fix concreto.
Veredito
CHANGES REQUESTED quando qualquer finding blocking, critical ou high sobrevive. PASS caso contrário — um PASS com findings medium e low é normal.
Como roda
Resolver a mudança contra o HEAD, o último commit antes da task → resolver as deferrals anteriores → ler os padrões que a mudança precisa cumprir → examinar cada arquivo alterado no seu contexto → montar o caso → aplicar três filtros que eliminam findings não comprovadas. A mudança é cobrada pelos critérios de aceite do ticket, além da testing strategy: um critério que o código não cumpre vira uma finding high.
Próximo passo
PASS sem findings → piv-commit [#N] [T-xx], nesta sessão ou em uma nova. PASS com findings medium ou low → piv-commit [#N] [T-xx], em uma sessão própria. CHANGES REQUESTED → piv-fix, em uma sessão própria, recebendo o caminho deste report.
Use antes de commitar uma task, e de novo depois de cada rodada de fix. Em um re-review, ela sobrescreve o report anterior: ele é o estado atual da task, e as decisões sobre findings antigas vivem nas deferrals, não ali.
Verify · triagem

piv-fix

Tria as findings do review, corrige uma a uma as que você escolher, com testes, adia as demais como deferrals locais, valida e escreve um fix report.

Input
[caminho do review report] — em branco, usa o review da task em andamento.
Output
tasks/T-xx/T-xx.fixes.md — Fixed, Deferred (com os D-xx), Needs a human look, Noise / won't-fix, e as checks executadas. Cada deferral vai para deferrals/D-xx.md e para a lista do epic; nenhuma issue é criada.
Como roda
Triar cada finding em um dos quatro grupos — uma finding blocking só em fix now ou noise, nunca adiada → corrigir o conjunto fix now uma de cada vez, cada uma com um teste que a comprove → validar a branch inteira.
Próximo passo
piv-review [#N] [T-xx] de novo, em uma sessão própria. Com uma entrada Needs a human look ainda aberta, o hand-off espera: inspecione-a e rode o piv-fix de novo.
Por que o report existe. A triagem é uma decisão humana, e uma decisão que vive só na conversa desaparece na próxima rodada. O fix report e os arquivos de deferral são o que dizem ao re-review que uma finding já foi resolvida — assim o que foi decidido permanece decidido.
Verify · commit, por task

piv-commit

Commita uma task revisada como commits atômicos e convencionalmente tagueados — cada um uma unidade coerente de trabalho que a subject line consiga nomear — e marca a task como concluída no epic.

Input
[#N | intent-slug] [T-xx] — em branco, pega a issue do nome da branch e a task em andamento do epic.
Output
Commits na branch do intent, cada subject terminando em (#N), mais um resumo "What Changed". A task vira [x] no epic, com os short hashes dos commits. A rodada termina com a árvore limpa.
Como roda
Conferir onde você está e se a árvore ainda bate com o PASS → inspecionar a árvore → agrupar as mudanças → commitar cada grupo → marcar a task como concluída.
Próximo passo
Ainda há task aberta → piv-implement [#N], em uma sessão própria. Todas concluídas → piv-open-pr [#N], nesta mesma sessão.
Use quando o veredito do review da task for PASS. Normalmente isso é um único commit; quando a árvore contém trabalho não relacionado, ela divide, e qualquer coisa que não caiba em nenhum grupo interrompe a rodada e pergunta a você.
Verify · entrega

piv-open-pr

Abre o pull request no GitHub para um intent com todas as tasks commitadas, fechando a issue no merge, e entrega a URL a um reviewer humano.

Input
[#N | intent-slug] · [base branch] — em branco, pega a issue do nome da branch e usa a base branch do projeto.
Output
Uma branch publicada e um PR aberto, com o label da issue e você como assignee. O body leva Closes #N, a revisão do spec e, por task, o resumo, a validação, os desvios, as findings que sobraram e os problemas em aberto — além de cada deferral por inteiro. Ela reporta o número do PR, a URL e as branches base ← head.
Como roda
Resolver o intent e a base branch → conferir que todas as tasks estão concluídas e todos os commits estão na branch → reunir o body a partir dos reports e das deferrals → publicar → abrir o PR com o gh.
Próximo passo
piv-review-pr [#N], em uma sessão própria — depois, um humano revisa, aprova e faz o merge.
A issue fecha sozinha. O Closes #N no body fecha a issue quando o PR é mergeado; nenhum passo a fecha à mão.
Verify · auditoria

piv-review-pr

Audita o PR aberto contra o spec, item por item, e escreve um PR review com veredito CONFORMS ou DIVERGES. Julga conformidade, não qualidade de código — o piv-review já fez isso, task por task.

Input
[#N | intent-slug] — em branco, pega a issue do nome da branch.
Output
.piv/[intent-slug]/pr-review.md — cada FR, NFR, C, D e AC marcado como met, diverges ou not verifiable, com a evidência; as divergências, inclusive mudanças fora do escopo, com severidade; os non-goals e as linhas Never, respeitados ou violados; e se o spec mudou depois que o PR abriu.
Como roda
Ler o PR com o gh, só leitura → indexar o spec → ler o diff inteiro → cobrar cada item contra ele → comparar as revisões do spec → escrever a review. Ela nunca comenta no PR.
Próximo passo
CONFORMS → um humano faz o merge. DIVERGES → você decide: corrigir à mão, planejar como um intent novo, ou aceitar. O loop do agent termina no merge.

Artifacts e onde eles vivem

Cada passo lê o artifact anterior, então os caminhos importam. Eles são definidos em docs/piv-loop.md, que a piv-setup instala junto com um docs/git-conventions.md mesclado com as regras de git que seu CLAUDE.md, AGENTS.md ou tooling de commit já definem. Por que local first

Um plano é barato de mudar enquanto é um arquivo, e caro quando vira um tracker cheio de tickets, comentários e links. Manter o spec, os tickets e todos os reports locais deixa o loop reescrevê-los livremente, e deixa no GitHub o que as pessoas de fato leem: uma issue que declara o intent e um PR que o entrega.

Por que uma issue, uma branch, um PR

O número da issue é a identidade do intent no git: a branch é [tag]/[N]-[intent-slug], todo commit termina em (#N), e o PR fecha a #N. Uma task é um commit nessa branch, então o histórico se lê task por task, e um humano revisa o intent inteiro uma vez, em vez de uma pilha de PRs pequenos.

O intent-slug

Todo artifact de um mesmo intent carrega o mesmo intent-slug: o kebab-slug do título do produto, ou do objetivo do spec, em ASCII minúsculo e sem acentos. Ele dá nome à pasta do intent em .piv/, e todo artifact abre com um header block — uma lista markdown curta, um campo em negrito por linha — que o carrega. Os passos seguintes leem o slug do artifact em vez de derivá-lo de novo — assim, um PRD escrito em user-auth/ nunca ganha um spec em authentication/ ao lado.

House rules

  1. Nada se encadeia sozinho. Cada skill termina oferecendo o próximo movimento; você o executa.
  2. Cada passo lê o artifact anterior. Reports são o input com que a próxima rodada trabalha, não burocracia.
  3. Skills param em vez de adivinhar. Um spec não revisado, uma task cuja dependência não foi commitada, uma árvore suja com trabalho que não cabe em nenhum grupo, o gh sem login — a rodada para e pergunta.
  4. O GitHub é escrito duas vezes. O piv-slice cria a issue e o piv-open-pr abre o PR; todo outro passo só lê, ou fica local.
  5. Review e fixes são rodadas separadas. O reviewer escreve as findings e não toca em código; a rodada de triagem decide o que acontece com cada uma, com você decidindo a divisão.
  6. Cada task fecha em um PASS. Uma rodada de fix sempre devolve para um review novo, que lê as deferrals para que o que foi decidido permaneça decidido.
  7. Uma task por vez. As tasks rodam na ordem do epic, nunca em paralelo, cada uma commitada antes de a próxima começar.
  8. Um idioma por intent. O PRD — ou, sem PRD, o spec — é escrito no idioma da entrevista, e todo artifact seguinte o acompanha. Os headings e rótulos dos templates ficam como os templates os escrevem.
Se uma rodada parar e perguntar algo

Isso é o design, não uma falha. Responda e rode de novo — adivinhar é a única coisa que estas skills não farão por você.

Um percurso completo

Um intent com duas tasks, do início ao merge. Cada linha é algo que você digita, e os passos estão agrupados pela sessão em que rodam; a nota ao lado de cada grupo diz por quê, e quais rodadas compartilham sessão explica o raciocínio.

  1. piv-write-prd — a entrevista e, ao final, um PRD em .piv/team-inbox/prd.md.

Sessão própria. O PRD é escrito em arquivo, e o próximo passo o lê de lá; nada precisa ficar na conversa.

  1. piv-spec .piv/team-inbox/prd.md — ela recebe o PRD como entrada; a entrevista e, ao final, um spec em .piv/team-inbox/spec.md.

Sessão nova. O PRD já guarda a intenção; a entrevista do spec parte do arquivo, não do contexto da entrevista do PRD.

  1. piv-review-spec team-inbox — ela encontra um PR aberto que se sobrepõe a um requisito; você resolve, e o spec fica reviewed.

Sessão nova. A review não pode dividir o contexto da entrevista.

  1. piv-slice team-inbox — dois tickets e o epic; você aprova a issue no gate, e a issue #123 abre com o spec no body.

Sessão nova. O slice só roda sobre o que a review aprovou, e o spec e a review já guardam tudo o que ele precisa.

  1. piv-implement #123 — a branch feat/123-team-inbox, a task T-01, os testes e tasks/T-01/T-01.report.md.

Sessão nova, uma por task. O passo mais pesado precisa da janela inteira; na sessão de planejamento ele deixaria passar as lacunas do ticket e traria de volta alternativas que as entrevistas rejeitaram.

  1. piv-review #123 — veredito CHANGES REQUESTED, 1 high e 3 medium em tasks/T-01/T-01.review.md.

Sessão nova, sempre. Na sessão da implementação, a review relê as próprias decisões e tende a confirmá-las.

  1. piv-fix .piv/team-inbox/tasks/T-01/T-01.review.md — você corrige a high e uma medium, adia duas como D-01 e D-02; o T-01.fixes.md registra cada decisão.

Sessão nova. A rodada que levantou os findings tende a defendê-los; a triagem precisa estar livre para decidir contra a review.

  1. piv-review #123 — ela lê as deferrals, e o veredito é PASS.

Sessão nova, sempre. Na sessão do fix, a review aprovaria a própria correção; só um PASS independente fecha o loop.

  1. piv-commit #123 — um commit terminando em (#123); a T-01 vira [x] no epic.

Sessão nova. O corpo do commit vem do diff, não dos reports. Depois, os passos 5–9 rodam de novo para a T-02.

  1. piv-commit #123 — a última task é commitada.
  2. piv-open-pr #123 — o PR abre com Closes #123 e as duas deferrals no body.

Uma sessão para os dois. Carregar um contexto do tamanho de uma review custa mais do que recomeçar; o PR descreve o que os commits registraram, então nada entre os dois precisa ficar independente.

  1. piv-review-pr #123 — todo item do spec está met: CONFORMS, e um humano faz o merge.

Sessão nova. A auditoria não pode dividir o contexto da rodada que entregou o que ela audita.

Os passos 6–8 se repetem quantas vezes uma task precisar, cada passada em sessões novas. Esse ciclo é o loop.

Quais rodadas compartilham sessão

Todo hand-off passa por um artifact — o spec, o epic, os tickets, os reports, os commits, o nome da branch — e nunca pela conversa. Uma sessão nova nunca perde o que o próximo passo precisa, então a escolha pesa duas coisas: se a próxima rodada precisa ser independente, e quanto a sessão custa em tokens.

Uma sessão compartilhada economiza a releitura de arquivos, mas cada turno reenvia a sessão inteira, e esse custo cresce a cada tool call. Uma sessão nova paga a releitura uma vez e deixa os turnos seguintes leves. Compartilhar só compensa quando o próximo passo vai reler quase tudo o que o anterior leu e a independência não importa — por isso só o último commit e o PR compartilham uma (e um commit com a review que terminou limpa).

Combinações a evitar

spec + review do spec: a entrevista julga a si mesma. implement + review: autoaprovação. review + fix: a triage não consegue decidir contra os findings. fix + re-review: o loop fecha sem um PASS independente. fix ou re-review + commit: uma sessão inchada e um body de commit que repete os reports. planejamento + implement: as lacunas do ticket passam despercebidas e alternativas descartadas voltam. open PR + review do PR: a auditoria herda a história do que foi entregue.

Solução de problemas

O review insiste em levantar algo que eu já decidi adiar.

O adiamento precisa existir como um arquivo em deferrals/ cujo Origin nomeia a task, não só como uma linha na conversa. O piv-fix escreve esses arquivos; o piv-review os lê no passo 2 dele. Se o arquivo não estiver lá, a finding volta com razão. Uma finding blocking volta mesmo quando adiada: ela só fecha com o fix, ou mostrando que o problema não existe.

O reviewer apontou algo que eu mudei de propósito.

Registre em Deviations from the ticket no implementation report. Essa seção é o sinal de intenção para o reviewer. A exceção é um teste que você alterou: desabilitado, afrouxado, reescrito ou removido, ele continua bloqueando o review.

Posso pular o PRD?

Pode. O PRD é uma entrada entre outras do piv-spec, e o spec é o que o resto do loop lê.

Posso rodar várias tasks ao mesmo tempo?

Não. As tasks dividem uma branch e são commitadas na ordem do epic, então cada review vê exatamente a mudança de uma task contra o último commit.

Editei o spec e agora o piv-slice para.

Esperado. A review aprovou uma revisão do spec, pelo hash; qualquer edição depois dela pede o piv-review-spec de novo.

O PR review diz DIVERGES. O piv-fix resolve?

Não. O piv-fix tria o review de uma task. Uma divergência no PR se corrige à mão na branch, se planeja como um intent novo, ou se aceita no merge — decisão sua.

Nada aconteceu depois que uma skill terminou.

Esperado. Skills não se encadeiam — leia o próximo movimento que ela ofereceu e execute-o você mesmo.
