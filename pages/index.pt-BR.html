Manual das Skills

O PIV Loop

Plan → Implement → Verify. Oito skills que levam uma ideia da página em branco até um pull request que um humano pode aprovar — um passo deliberado por vez.

O que é o PIV loop

PIV significa plan → implement → verify. É o formato pelo qual as skills deste projeto conduzem o trabalho.

  • Plan transforma uma ideia em um spec e um conjunto de tickets.
  • Implement constrói um ticket na própria branch e escreve um implementation report.
  • Verify tenta provar que a mudança está errada antes que ela vá para produção: um review escreve as findings, uma rodada de triagem resolve cada uma, e só então o trabalho é commitado e entregue a um humano.

Duas propriedades sustentam o conjunto. Cada passo lê o artifact que o passo anterior escreveu — os reports não são burocracia, são o input. E cada passo é iniciado por você, nunca pelo passo anterior.

A ideia central

Nada se encadeia sozinho. Cada skill termina dizendo qual é o próximo movimento; você decide se o executa. É isso que impede um plano ruim de virar um PR mergeado enquanto você estava longe.

A chain em um relance

Plan
piv-spec → piv-slice
Implement
piv-implement
Verify
piv-review → piv-fix → piv-commit → piv-open-pr

O loop fecha em um PASS. piv-fix sempre devolve para um piv-review novo. Só um veredito PASS conquista um commit.

Leia as setas como "este é o próximo movimento oferecido", não como automação. As três skills de verify antes do PR são o gate; o PR em si é a entrega para fora do loop, para um humano que revisa, aprova e faz o merge.

Por onde começar?

Raramente você precisa das oito. Encontre a linha que corresponde ao que você tem em mãos.

Setup

O setup não é um passo do loop: roda uma vez por projeto, antes do primeiro passo, e de novo sempre que chegar uma versão mais nova das skills.

Instale as skills a partir da raiz do seu projeto com um único comando. Ele exige Node.js e git, em Windows com Git Bash, macOS ou Linux, e instala só para o Claude Code. Depois, rode /piv-setup.

npx skills@1.7.2 add fabianosobreira/piv-pipeline#releases -s '*' -a claude-code --copy -y
  • Faça o commit do lock file junto com as skills. O comando cria o skills-lock.json na raiz do projeto; faça o commit dele junto com o .claude/skills/.
  • Não ponha arquivos seus nas pastas piv-*. Cada pasta .claude/skills/piv-*/ é substituída inteira a cada execução, então um arquivo que você acrescentar ali é apagado.
  • Uma instalação que falhou se recupera rodando o comando de novo.
  • Para atualizar, rode o mesmo comando de novo. Ele não fixa versão: instala o estado atual da branch releases, e o lock file registra só o hash instalado. Para fixar uma versão à mão, troque #releases por #vX.Y.Z.
Setup · uma vez por projeto

piv-setup

Instala no docs/ do projeto os docs que todo passo lê, e incorpora ao docs/git-conventions.md as regras de git que o projeto já tem — as suas regras vencem os defaults que vêm com a skill.

Input
[github | gitlab | jira | md] — em branco, sugere um a partir do git remote.
Output
docs/piv-loop.md; docs/issue-tracker.md do tracker que você escolher, com os dados do projeto preenchidos; docs/git-conventions.md; e um docs/.gitignore que mantém os planos e os reports fora do git. Depois, um commit, se você aprovar.
Como roda
Investigar os docs existentes, o remote e o harness → rascunhar o docs/git-conventions.md → apresentar o plano inteiro em um único gate → instalar → mostrar a mensagem de commit e esperar por você.
Guards
  • O harness vence — regras de git de CLAUDE.md, AGENTS.md, arquivos de regras e tooling de commit prevalecem sobre o git-conventions.md que vem com a skill; cada uma guarda a nota de onde veio.
  • As necessidades das skills são conferidas — base branch, formato do commit subject, formato do PR title e as commit tags são obrigatórios; uma regra que quebre um deles volta para você. Branch name ou subject sem o ticket id são permitidos, ao custo de as skills pedirem o id a cada rodada.
  • Nada é sobrescrito em silêncio — um docs/issue-tracker.md existente é mantido ou substituído conforme você decidir, e um docs/.gitignore existente só ganha as linhas que faltam.
Próximo passo
Nenhum no loop: termina no commit. Escolha o ponto de partida em Por onde começar?
Use
  • Logo depois de instalar as skills num repo com o comando acima.
  • Quando suas regras de git vivem em CLAUDE.md ou AGENTS.md — ela pode movê-las para o docs/git-conventions.md e deixar um ponteiro no lugar, se você aceitar.
  • Quando chegar uma versão mais nova das skills e os docs precisarem acompanhar.

Plan

A etapa de plan produz dois tipos de documento: o spec, que fixa requisitos, design, tasks e verificação em um só arquivo, e as unidades de trabalho (os tickets), cada um uma fatia literal desse spec. São skills separadas porque respondem a perguntas diferentes. O piv-write-prd fica à parte: um PRD opcional que só o piv-spec lê.

Plan · passo 1

piv-spec

Entrevista você em fases fixas até os dois lados confirmarem o mesmo entendimento, e então escreve um spec de 10 seções que o piv-slice corta em tickets. Toda afirmação vem de uma resposta sua; o agent nunca preenche uma lacuna.

Entrada
[intent-slug] e, opcionalmente, o caminho de um PRD escrito pelo piv-write-prd. Em branco, começa com perguntas.
Saída
docs/.plans/[intent-slug].spec.md — objetivo, non-goals, requisitos funcionais (FR), não funcionais (NFR), acceptance criteria (AC), restrições (C), design (D), plano de tasks (T), comandos de verificação, limites e um decision log. Intent-slug e Language ficam no cabeçalho.
Como roda
Oito fases de perguntas numeradas; todo statement remete a uma resposta sua. Um validador incluso checa estrutura e rastreabilidade: todo NFR, C e D precisa ser citado por uma task, e toda referência precisa resolver. Status: ready assim que o lint fica limpo.
Próximo passo
piv-slice [caminho do spec], nesta sessão ou em uma nova.
Use quando
  • Você tem uma mudança em mente, com ou sem PRD, e quer fixá-la antes que alguém construa.
  • Um AI agent vai implementá-la e precisa de requisitos que consiga verificar.
Pule quando a mudança for uma correção de uma linha que você mesmo descreve num ticket.
Plan · passo 2

piv-slice

Corta um spec pronto em tickets e os cria no tracker do projeto. Cada ticket copia, linha por linha, a parte do spec de que sua task precisa — nada é criado nem reescrito. É também aqui que o epic nasce, quando a divisão tem mais de um ticket.

Entrada
O caminho de um spec escrito pelo piv-spec, com Status: ready. Um spec ainda em draft encerra a execução.
Saída
Um ticket por task, cada um com um header block (Spec com o hash da revisão, Slice, Blocked by, Size, Intent-slug, Language) e as seções do spec. Com mais de um ticket, um epic lista os tickets, o grafo de dependências e o que não virou ticket. O spec e o PRD nunca são publicados.
Como roda
Sem interação durante o corte e o mapeamento de dependências, e então um gate em que você confirma a divisão. Um validador incluso, o lint_ticket.sh, rejeita toda linha de ticket que não seja uma linha literal do spec, e nenhum ticket é criado até todos os rascunhos passarem.
Próximo passo
piv-implement [ticket-id], em uma sessão própria, uma por ticket — ou uma onda de tickets independentes em paralelo, cada um em uma sessão própria.
Use quando um spec estiver pronto e você precisar fatiá-lo em unidades que um agent consiga terminar e comprovar. Cada ticket leva o que precisa, então o spec fica na sua máquina.
Avulsa

piv-write-prd

Entrevista você para fixar o problema, o porquê de construí-lo e uma hipótese falseável — e então escreve um PRD em nível de produto. Só intent: o quê e por quê, nunca decisões de engenharia. Não é um passo do loop: só o piv-spec lê o PRD, como contexto opcional.

Input
[ideia de produto] e, opcionalmente, caminhos para research docs — entrevistas com usuários, temas de tickets de suporte, analytics, análises de concorrentes. Em branco, começa pelas perguntas.
Output
docs/.plans/[intent-slug].prd.md — problem statement, evidências, tese, hipótese, usuário-alvo e JTBD, restrições, MVP, métricas de sucesso, não-objetivos, questões em aberto.
Como roda
Uma entrevista agrupada em cinco fases, cada uma terminando em um gate onde ela espera por você. As perguntas são numeradas ao longo de toda a rodada, e a hipótese volta para você, montada com as suas próprias palavras, antes de ser fechada.
Guards
  • Evidence-or-TBD — todo requisito rastreia até algo que você disse ou que um doc mostrou; o que é desconhecido é escrito como "TBD — needs validation".
  • Intent-framed, não solution-prescriptive — se só uma solução couber no problem statement, aquilo é uma spec, não um PRD.
Próximo passo
piv-spec [intent-slug] [caminho do PRD], nesta sessão ou em uma nova.
Use quando
  • Você está começando algo greenfield e ninguém escreveu o problema ainda.
  • Você está dimensionando um trabalho novo num produto existente — o research doc, o decision plan ou os docs do produto que trazem o contexto viram o input.
  • Duas pessoas do time descreveriam "o problema" de formas diferentes.
Pule quando a mudança já estiver clara o bastante para ir direto ao piv-spec.

Implement

Implement

piv-implement

Constrói um ticket, task por task, na própria branch, validando a cada passo, e escreve um implementation report.

Input
[ticket id]. Em branco, ela pergunta qual ticket.
Output
docs/.reports/[ticket-id]-report.md — resumo, tasks concluídas, testes adicionados, resultados de validação, desvios em relação ao ticket, problemas encontrados. O status é COMPLETE ou PARTIAL — PARTIAL também quando um arquivo alterado é ignorado pelo git, porque ele nunca viaja com a branch.
Como roda
Resolver o ticket → trabalhar em uma branch → ler o ticket de ponta a ponta e checar o drift → executar as tasks em ordem → fechar a estratégia de testes → rodar as checks → verificação final.
Próximo passo
piv-review, em uma sessão própria, recebendo o ticket id.
Por que os desvios importam. O reviewer lê este report. Um desvio registrado aqui é uma decisão intencional que o reviewer não deve apontar; o mesmo desvio não escrito volta como uma finding. A exceção é um teste: um teste desabilitado, afrouxado, reescrito ou removido continua bloqueando o review, mesmo quando um desvio o explica.

Verify

Verify são quatro skills e uma regra: review e fixes são rodadas separadas. O reviewer escreve findings e não toca em código. A rodada de triagem decide o que acontece com cada uma, com você decidindo a divisão.

Verify · o gate

piv-review

Revisa a mudança pronta em busca de bugs, defeitos de segurança e violações de padrões, e escreve um review report. É um report, nunca uma edição.

Input
[ticket id] — em branco, é extraído do nome da branch.
Output
docs/.reports/[ticket-id]-review.md — escopo (todo arquivo lido), findings agrupadas em blocking / critical / high / medium / low, e as checks executadas, entre elas a suíte de testes completa. Uma finding blocking é um teste vermelho, faltando ou enfraquecido, ou uma behavior sem teste — um fato, fora da escala de severidade. Cada finding carrega evidência, impacto e um fix concreto.
Veredito
CHANGES REQUESTED quando qualquer finding blocking, critical ou high sobrevive. PASS caso contrário — um PASS com findings medium e low é normal.
Como roda
Resolver a mudança → resolver as deferrals anteriores → ler os padrões que a mudança precisa cumprir → examinar cada arquivo alterado no seu contexto → montar o caso → aplicar três filtros que eliminam findings não comprovadas. A mudança é cobrada pelos critérios de aceite do ticket, além da testing strategy: um critério que o código não cumpre vira uma finding high.
Próximo passo
PASS → piv-commit, em uma sessão própria. CHANGES REQUESTED → piv-fix, em uma sessão própria, recebendo o caminho deste report.
Use antes de commitar qualquer coisa, e de novo depois de cada rodada de fix. Em um re-review, ela sobrescreve o report anterior: ele é o estado atual da branch, e as decisões sobre findings antigas vivem no tracker, não ali.
Verify · triagem

piv-fix

Tria as findings do review, corrige uma a uma as que você escolher, com testes, adia e registra as demais no tracker, valida e escreve um fix report.

Input
[caminho do review report] — em branco, usa o review escrito para esta branch.
Output
docs/.reports/[ticket-id]-fixes.md — Fixed, Deferred (com as referências das issues), Needs a human look, Noise / won't-fix, e as checks executadas.
Como roda
Triar cada finding em um dos quatro grupos — uma finding blocking só em fix now ou noise, nunca adiada → corrigir o conjunto fix now uma de cada vez, cada uma com um teste que a comprove → validar a branch inteira.
Próximo passo
piv-review de novo, em uma sessão própria, recebendo o ticket id.
Por que o report existe. A triagem é uma decisão humana, e uma decisão que vive só na conversa desaparece na próxima rodada. O fix report e as issues de deferral são o que dizem ao re-review que uma finding já foi resolvida — assim o que foi decidido permanece decidido.
Verify · commit

piv-commit

Commita o trabalho pronto como commits atômicos e convencionalmente tagueados — cada um uma unidade coerente de trabalho que a subject line consiga nomear.

Input
[ticket id] — em branco, é extraído do nome da branch.
Output
Commits na branch, mais um resumo "What Changed" para quem for percorrer o git log. A rodada termina com a árvore limpa.
Como roda
Conferir onde você está → inspecionar a árvore → agrupar as mudanças → commitar cada grupo → acrescentar um body quando a subject não bastar.
Próximo passo
piv-open-pr, nesta mesma sessão. O ticket id viaja no nome da branch, e é de lá que a próxima skill o lê.
Use quando o veredito do review for PASS. Normalmente isso é um único commit; quando a árvore contém trabalho não relacionado, ela divide, e qualquer coisa que não caiba em nenhum grupo interrompe a rodada e pergunta a você.
Verify · entrega

piv-open-pr

Abre o pull request da branch finalizada e entrega a URL a um reviewer humano.

Input
[base branch] · [ticket id] — em branco, usa a base branch do projeto, com o ticket id lido do nome da branch.
Output
Uma branch publicada e um review request aberto: resumo, o que mudou, validação, notas para o reviewer, questões em aberto, ticket vinculado. Ela reporta o número do PR, a URL e as branches base ← head.
Como roda
Resolver a base branch → conferir se a branch está entregável → reunir o body a partir dos reports → publicar → abrir o review request.
Próximo passo
Um humano revisa, aprova e faz o merge. O loop do agent termina no merge.
Portável por design. Um pull request no GitHub, um merge request no GitLab, ou marcar uma branch como pronta para review em outro lugar — ela usa o ferramental que o repo já usa.

Artifacts e onde eles vivem

Cada passo lê o artifact anterior, então os caminhos importam. Eles são definidos em docs/issue-tracker.md.

docs/issue-tracker.md é seu para customizar — é onde um projeto declara qual tracker usa e quais são os caminhos dos artifacts, e as skills leem esse nome de arquivo e nenhum outro. A piv-setup o escreve para o tracker que você escolher — GitHub, GitLab, Jira ou arquivos markdown locais —, junto com docs/piv-loop.md, um docs/git-conventions.md mesclado com as regras de git que seu CLAUDE.md, AGENTS.md ou tooling de commit já definem, e um docs/.gitignore que mantém os planos e os reports fora do git. Rode-a uma vez antes do primeiro passo, e de novo para receber uma versão mais nova.

O intent-slug

Todo artifact de um mesmo intent carrega o mesmo intent-slug: o kebab-slug do título do epic ou do produto, em ASCII minúsculo e sem acentos. Todo artifact abre com um header block — uma lista markdown curta, um campo em negrito por linha — e o slug é o primeiro campo dela. Os passos seguintes leem o slug do artifact em vez de derivá-lo de novo — assim, um PRD escrito como user-auth.prd.md nunca ganha um authentication.spec.md ao lado.

House rules

  1. Nada se encadeia sozinho. Cada skill termina oferecendo o próximo movimento; você o executa.
  2. Cada passo lê o artifact anterior. Reports são o input com que a próxima rodada trabalha, não burocracia.
  3. Skills param em vez de adivinhar. Nenhum tracker escolhido, um ticket id ambíguo, uma árvore suja com trabalho que não cabe em nenhum grupo, um review report que não existe — a rodada para e pergunta.
  4. Review e fixes são rodadas separadas. O reviewer escreve as findings e não toca em código; a rodada de triagem decide o que acontece com cada uma, com você decidindo a divisão.
  5. O loop fecha em um PASS. Uma rodada de fix sempre devolve para um review novo, que lê as issues de deferral para que o que foi decidido permaneça decidido.
  6. Um idioma por intent. O PRD — ou, sem PRD, o spec — é escrito no idioma da entrevista, e todo artifact seguinte o acompanha. Os headings e rótulos dos templates ficam como os templates os escrevem.
Se uma rodada parar e perguntar algo

Isso é o design, não uma falha. Responda e rode de novo — adivinhar é a única coisa que estas skills não farão por você.

Um percurso completo

Um epic, do início ao merge. Cada linha é algo que você digita, e os passos estão agrupados pela sessão em que rodam; a nota ao lado de cada grupo diz por quê, e quais rodadas compartilham sessão explica o raciocínio.

  1. piv-write-prd — a entrevista e, ao final, um PRD em docs/.plans/team-inbox.prd.md.
  2. piv-spec team-inbox docs/.plans/team-inbox.prd.md — a entrevista e, ao final, um spec em docs/.plans/team-inbox.spec.md.
  3. piv-slice docs/.plans/team-inbox.spec.md — confirme a divisão no gate; os tickets vão para o tracker.

Uma sessão para os três. Eles colaboram em vez de auditar um ao outro, e a nuance da entrevista segue junto. Se a janela passar da metade, quebre na fronteira de um doc — os docs já guardam tudo.

  1. piv-implement 123 — uma branch, as tasks, os testes e docs/.reports/123-report.md.

Sessão nova, uma por ticket. O passo mais pesado precisa da janela inteira; na sessão de planejamento ele deixaria passar as lacunas do ticket e traria de volta alternativas que as entrevistas rejeitaram.

  1. piv-review 123 — veredito CHANGES REQUESTED, 1 high e 3 medium em docs/.reports/123-review.md.

Sessão nova, sempre. Na sessão da implementação, a review relê as próprias decisões e tende a confirmá-las.

  1. piv-fix docs/.reports/123-review.md — você corrige a high e uma medium, adia duas no tracker; docs/.reports/123-fixes.md registra cada decisão.

Sessão nova. A rodada que levantou os findings tende a defendê-los; a triagem precisa estar livre para decidir contra a review.

  1. piv-review 123 — ela lê as issues de deferral, e o veredito é PASS.

Sessão nova, sempre. Na sessão do fix, a review aprovaria a própria correção; só um PASS independente fecha o loop.

  1. piv-commit 123 — commits atômicos, árvore limpa.
  2. piv-open-pr — o PR abre e a URL vai para um humano.

Uma sessão nova para os dois. Carregar um contexto do tamanho de uma review custa mais do que recomeçar, e o corpo do commit vem do diff, não dos reports. O PR descreve o que o commit registrou, então nada entre os dois precisa ficar independente.

Os passos 5–7 se repetem quantas vezes a branch precisar, cada passada em sessões novas. Esse ciclo é o loop.

Quais rodadas compartilham sessão

Todo hand-off passa por um artifact — o spec, os tickets, os reports, os commits, o nome da branch — e nunca pela conversa. Uma sessão nova nunca perde o que o próximo passo precisa, então a escolha pesa duas coisas: se a próxima rodada precisa ser independente, e quanto a sessão custa em tokens.

Uma sessão compartilhada economiza a releitura de arquivos, mas cada turno reenvia a sessão inteira, e esse custo cresce a cada tool call. Uma sessão nova paga a releitura uma vez e deixa os turnos seguintes leves. Compartilhar só compensa quando o próximo passo vai reler quase tudo o que o anterior leu e a independência não importa — por isso só os passos de planejamento, e o commit com o PR, compartilham uma.

Combinações a evitar

implement + review: autoaprovação. review + fix: a triage não consegue decidir contra os findings. fix + re-review: o loop fecha sem um PASS independente. fix ou re-review + commit: uma sessão inchada e um body de commit que repete os reports. planejamento + implement: as lacunas do ticket passam despercebidas e alternativas descartadas voltam.

Solução de problemas

O review insiste em levantar algo que eu já decidi adiar.

O adiamento precisa existir como uma issue no tracker, não só como uma linha na conversa. piv-fix abre essas issues; piv-review as lê no passo 2 dele. Se a issue não estiver lá, a finding volta com razão. Uma finding blocking volta mesmo quando adiada: ela só fecha com o fix, ou mostrando que o problema não existe.

O reviewer apontou algo que eu mudei de propósito.

Registre em Deviations from the ticket no implementation report. Essa seção é o sinal de intenção para o reviewer. A exceção é um teste que você alterou: desabilitado, afrouxado, reescrito ou removido, ele continua bloqueando o review.

Posso pular o PRD?

Pode. O PRD é contexto opcional do piv-spec, e o spec é o que o resto do loop lê.

Posso rodar vários tickets ao mesmo tempo?

Pode. piv-slice mapeia as dependências no passo 4 justamente para que você veja quais tickets formam uma leva independente.

Nada aconteceu depois que uma skill terminou.

Esperado. Skills não se encadeiam — leia o próximo movimento que ela ofereceu e execute-o você mesmo.
