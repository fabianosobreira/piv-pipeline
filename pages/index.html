Skills Manual

The PIV Loop

Plan → Implement → Verify. Ten skills that carry an idea from a blank page to a pull request a human can approve — one deliberate step at a time, on your machine, with GitHub as the only remote.

What the PIV loop is

PIV stands for plan → implement → verify. It is the shape this project's skills run work through.

  • Plan turns an idea into a spec, audits it against your code and your GitHub issues and PRs, cuts it into one ticket per task, and publishes it as one GitHub issue.
  • Implement builds one task at a time on the intent's branch and writes an implementation report.
  • Verify tries to prove each task wrong before it is committed: a review writes findings, a triage run settles each one, and only then is the task committed. Once every task is in, the PR opens and is audited against the spec before a human merges it.

Two properties hold the whole thing together. Every step reads the artifact the step before it wrote — the reports are not paperwork, they are the input. And every step is started by you, never by the step before it.

The core idea

Nothing chains itself. Each skill finishes by telling you the next move; you decide whether to run it. That is what keeps a bad plan from becoming a merged PR while you were away.

The chain at a glance

Plan
piv-spec → piv-review-spec → piv-slice
Implement
piv-implement

One task at a time. Implement, review, fix and commit repeat for each task of the epic, in its order.

Verify
piv-review → piv-fix → piv-commit → piv-open-pr → piv-review-pr

Each task closes on a PASS. piv-fix always hands back to a fresh piv-review. Only a PASS verdict earns a commit; the PR opens once every task is committed.

Read the arrows as "this is the next move offered", not as automation. The review, the triage and the commit are the gate for each task; the PR is the handoff out of the loop, to a human who reviews, approves and merges.

Setup

Setup is not a step of the loop: it runs once per project, before the first step, and again whenever a newer version of the skills arrives.

Install the skills from the root of your project with one command. It needs Node.js and git, on Windows with Git Bash, macOS or Linux, and it installs for Claude Code only. Then run /piv-setup.

npx skills@1.7.2 add fabianosobreira/piv-pipeline#releases -s '*' -a claude-code --copy -y
  • Commit the lock file with the skills. The command writes skills-lock.json at the project root; commit it together with .claude/skills/.
  • Keep your own files out of the piv-* folders. Each .claude/skills/piv-*/ folder is replaced whole on every run, so a file you add there is deleted.
  • A failed install is recovered by running the command again.
  • To update, run the same command again. It pins no version: it installs the current state of the releases branch, and the lock file records only the hash installed. To pin a version by hand, replace #releases with #vX.Y.Z.
Setup · once per project

piv-setup

Checks that the project is on GitHub with gh logged in, installs the docs every step reads into the project's docs/, folds the git rules the project already has into docs/git-conventions.md — your rules win over the shipped defaults — and has git ignore .piv/.

Input
None.
Output
docs/piv-loop.md; docs/git-conventions.md; and the line .piv/ in the root .gitignore, created when absent. Then one commit, if you approve it.
How it runs
Check the remote and gh, investigate the existing docs and the harness → draft docs/git-conventions.md → post the whole plan at one gate → install → show the commit message and wait for you.
Guards
  • GitHub or nothing — an origin off github.com, or gh not logged in, stops the run with the command that fixes it.
  • The harness wins — git rules from CLAUDE.md, AGENTS.md, rules files and commit tooling override the shipped git-conventions.md; each one keeps a note of where it came from.
  • The skills' needs are checked — a base branch, a commit subject form, a PR title form and the commit tags are required; a rule that breaks one comes back to you. A branch name or subject without the issue number is allowed, at the cost of the skills asking you for the issue every run.
  • Nothing overwritten silently — an existing .gitignore only gains the .piv/ line.
Next move
None in the loop: it ends on the commit. Pick your starting point from Where do I start?
Use it when
  • You have just installed the skills into a repo with the command above.
  • Your git rules live in CLAUDE.md or AGENTS.md — it can move them into docs/git-conventions.md and leave a pointer behind, at your word.
  • A newer version of the skills arrived and the docs should follow.

Plan

The plan step produces the spec, which fixes requirements, design, tasks and verification in one file; its review, which checks it against what already exists; and the tickets, each a verbatim slice of the spec for one task, tracked by a local epic and published as one GitHub issue. They are separate skills because they answer different questions. piv-write-prd stands apart: its PRD is an ordinary input of piv-spec, handed over by path.

Plan · step 1

piv-spec

Interviews you in fixed phases, then writes one 10-section spec. Every statement comes from an answer you gave; the agent never fills a gap.

Input
[intent-slug] and the concept — a paragraph, a file, or a full document with links. URLs you pass are read without asking; links it finds on its own are asked first. A PRD is one such document: pass its path, .piv/[intent-slug]/prd.md, and its folder is reused. Blank starts with questions.
Output
.piv/[intent-slug]/spec.md — goal, non-goals, functional requirements (FR), non-functional requirements (NFR), acceptance criteria (AC), constraints (C), design (D), task plan (T), verification commands, boundaries and a decision log. Intent-slug and Language sit in its header.
How it runs
Eight phases of numbered questions; every statement traces to an answer you gave. A bundled validator checks structure and traceability: every NFR, C and D must be cited by a task, and every reference must resolve. Status: ready once the lint is clean.
Next move
piv-review-spec [intent-slug], in a session of its own.
Use it when
  • You have a change in mind, with or without a PRD, and want it pinned down before anyone builds.
  • An AI agent will implement it and needs requirements it can verify.
Skip it when the change is a one-line fix you can make by hand.
Plan · step 2

piv-review-spec

Audits a ready spec before it is published: what the codebase already holds, what the repo's issues and PRs already say, and every item the interview left deferred. It settles each one with you, and marks the spec's revision reviewed.

Input
[intent-slug], for a spec with Status: ready. A draft stops the run.
Output
The spec, edited only with your answers, at Status: reviewed; and .piv/[intent-slug]/spec.review.md — what exists in the code, the conflicting issues and PRs, what you settled, what changed, and the Reviewed-hash of the spec. A problem that needs a new interview reopens the spec as draft instead.
How it runs
Read the spec → search the codebase → search the repo's issues and PRs with gh, read-only → ask, in the same numbered format as piv-spec → apply the answers and lint → mark the outcome. Without gh logged in it stops, unless you rule to go on without the remote check.
Next move
piv-slice [intent-slug], in a session of its own.
Why a separate run. The interview that wrote the spec is the worst judge of it. A fresh session finds the code that already does half the job, and the closed issue that already rejected the idea, before the spec becomes a public issue.
Plan · step 3

piv-slice

Cuts a reviewed spec into one ticket per task and an epic that tracks them, then publishes the spec as the intent's one GitHub issue. Each ticket copies, line for line, the part of the spec its task needs — nothing is created or reworded.

Input
[intent-slug], for a spec at Status: reviewed whose hash matches its review. A draft, a ready, or a spec edited after its review stops the run.
Output
tasks/T-xx/T-xx.md, one ticket per task, each with a header block (Spec with the revision hash, Task, Type, Blocked by, Size, Intent-slug, Language) and the spec's sections; epic.md, the to-do list of tasks; and one GitHub issue, with the whole spec as its body, one type label — bug, feature or task — and you as assignee.
How it runs
Non-interactive through slicing, linting and the gh preflight, then one gate where you approve the issue: its title, its type, and the warning that the spec is published in full. A bundled validator, lint_ticket.sh, rejects any ticket line that is not a verbatim line of the spec, and any ticket with more than one task; nothing reaches GitHub until every ticket passes.
Next move
piv-implement [#N], in a session of its own.
Use it when a spec is reviewed and you need it sliced into units an agent can finish and prove, one at a time.
Standalone

piv-write-prd

Interviews you to pin down the problem, why to build it, and a falsifiable hypothesis — then writes a product-level PRD. Intent only: what and why, never engineering decisions. It is not a step of the loop: its PRD is an ordinary input of piv-spec, handed over by path.

Input
[product idea] plus optional paths to research docs — user interviews, support-ticket themes, analytics, competitor teardowns. Blank starts with questions.
Output
.piv/[intent-slug]/prd.md — problem statement, evidence, thesis, hypothesis, target user & JTBD, constraints, MVP, success metrics, non-goals, open questions.
How it runs
A clustered interview in five phases, each ending at a gate where it waits for you. Questions are numbered across the whole run, and the hypothesis comes back to you assembled from your own words before it is final.
Guards
  • Evidence-or-TBD — every requirement traces to something you said or a doc showed; unknowns are written as "TBD — needs validation".
  • Intent-framed, not solution-prescriptive — if only one solution could fit the problem statement, it's a spec, not a PRD.
Next move
piv-spec .piv/[intent-slug]/prd.md, in a session of its own.
Use it when
  • You're starting something greenfield and no one has written down the problem yet.
  • Two people on the team would describe "the problem" differently.
Skip it when the change is already clear enough to go straight to piv-spec.

Implement

Implement · per task

piv-implement

Builds one task from its ticket on the intent's branch, validating at every step, and writes an implementation report. The work stays uncommitted for the review.

Input
[#N | intent-slug] [T-xx]. Blank takes the issue from the branch name and the next task from the epic: the one in progress, else the first whose dependencies are all committed.
Output
tasks/T-xx/T-xx.report.md — summary, tasks completed, tests added, validation results, deviations from the ticket, problems encountered. Status is COMPLETE or PARTIAL — PARTIAL also when a changed file is one git ignores, since it never travels with the branch. The task turns [~] in the epic.
How it runs
Resolve the task and check its dependencies → work on the intent's branch, created by the first task as [tag]/[N]-[intent-slug] → read the ticket end to end and check for drift → execute tasks in order → close the testing strategy → run the checks → final verification.
Next move
piv-review [#N] [T-xx], in a session of its own.
Why deviations matter. The reviewer reads this report. A deviation recorded here is an intentional decision the reviewer should not flag; the same deviation left unwritten comes back as a finding. The exception is a test: one skipped, loosened, rewritten or deleted still blocks the review, even when a deviation explains it.

Verify

Verify is five skills and one rule: review and fixes are separate runs. The reviewer writes findings and touches no code. The triage run decides what happens to each finding, with you ruling on the split. Review, triage and commit run per task; the PR and its audit run once, for the whole intent.

Verify · the gate, per task

piv-review

Reviews one task's uncommitted change for bugs, security defects and standards violations, and writes a review report. It is a report, never an edit.

Input
[#N | intent-slug] [T-xx] — blank and it takes the issue from the branch name and the task in progress from the epic.
Output
tasks/T-xx/T-xx.review.md — scope (every file read), findings grouped blocking / critical / high / medium / low, and the checks run, the full test suite among them. A blocking finding is a red, missing or weakened test, or a behavior with no test — a fact, outside the severity scale. Each finding carries evidence, impact and a concrete fix.
Verdict
CHANGES REQUESTED when any blocking, critical or high finding survives. PASS otherwise — a PASS with medium and low findings is normal.
How it runs
Resolve the change against HEAD, the last commit before the task → resolve prior deferrals → read the standards the change must meet → examine every changed file in its context → build the case → run three filters that kill unproven findings. The change is held to the ticket's acceptance criteria as well as its testing strategy: a criterion the code doesn't meet is a high finding.
Next move
PASS with no findings → piv-commit [#N] [T-xx], here or in a fresh session. PASS with medium or low findings → piv-commit [#N] [T-xx], in a session of its own. CHANGES REQUESTED → piv-fix, in a session of its own, handed this report's path.
Use it before committing a task, and again after every fix run. On a re-review it overwrites the previous report: it is the current state of the task, and the rulings on old findings live in the deferrals, not here.
Verify · triage

piv-fix

Triages the review's findings, fixes the ones you choose one at a time with tests, defers the rest as local deferrals, validates, and writes a fix report.

Input
[review report path] — blank and it uses the review of the task in progress.
Output
tasks/T-xx/T-xx.fixes.md — Fixed, Deferred (with their D-xx), Needs a human look, Noise / won't-fix, and the checks run. Each deferral lands in deferrals/D-xx.md and in the epic's list; no issue is created.
How it runs
Triage every finding into one of the four buckets — a blocking finding only into fix now or noise, never deferred → fix the fix now set one at a time, each with a test that proves it → validate the whole branch.
Next move
piv-review [#N] [T-xx] again, in a session of its own. With a Needs a human look entry still open, the hand-off waits: inspect it, then rerun piv-fix.
Why the report exists. Triage is a human decision, and a decision that lives only in the conversation is gone by the next run. The fix report and the deferral files are what tell the re-review that a finding was already settled — so settled findings stay settled.
Verify · commit, per task

piv-commit

Commits one reviewed task as atomic, conventionally-tagged commits — each one a coherent piece of work its subject line can name — and marks the task done in the epic.

Input
[#N | intent-slug] [T-xx] — blank and it takes the issue from the branch name and the task in progress from the epic.
Output
Commits on the intent's branch, each subject closing on (#N), plus a "What Changed" summary. The task turns [x] in the epic, with its commits' short hashes. The run ends with a clean tree.
How it runs
Check where you are and that the tree still matches the PASS → inspect the tree → group the changes → commit each group → mark the task done.
Next move
A task still open → piv-implement [#N], in a session of its own. Every task done → piv-open-pr [#N], in this same session.
Use it once the task's review verdict is PASS. Usually this is a single commit; when the tree holds unrelated work it splits, and anything that fits no group stops the run and asks you.
Verify · handoff

piv-open-pr

Opens the GitHub pull request for an intent whose tasks are all committed, closing its issue on merge, and hands the URL to a human reviewer.

Input
[#N | intent-slug] · [base branch] — blank and it takes the issue from the branch name and uses the project's base branch.
Output
A published branch and an open PR, with you as assignee. Its body carries Closes #N, the spec's revision, and per task the summary, validation, deviations, surviving findings and open problems — plus every deferral in full. It reports the PR number, the URL and the base ← head branches.
How it runs
Resolve the intent and the base branch → check every task is done and every commit is on the branch → gather the body from the reports and the deferrals → publish → open the PR with gh.
Next move
piv-review-pr [#N], in a session of its own — then a human reviews, approves and merges.
The issue closes itself. Closes #N in the body closes the issue when the PR merges; no step closes it by hand.
Verify · audit

piv-review-pr

Audits the open PR against the spec, item by item, and writes a PR review with a CONFORMS or DIVERGES verdict. It judges conformance, not code quality — piv-review already did that, task by task.

Input
[#N | intent-slug] — blank and it takes the issue from the branch name.
Output
.piv/[intent-slug]/pr-review.md — every FR, NFR, C, D and AC marked met, diverges or not verifiable with its evidence; the divergences, out-of-scope changes included, with a severity; the non-goals and Never lines, respected or violated; and whether the spec changed after the PR opened.
How it runs
Read the PR with gh, read-only → index the spec → read the whole diff → hold every item to it → compare the spec's revisions → write the review. It never comments on the PR.
Next move
CONFORMS → a human merges. DIVERGES → you decide: fix it by hand, plan it as a new intent, or accept it. The agent's loop ends at the merge.

Why local first

A plan is cheap to change while it is a file and expensive once it is a tracker full of tickets, comments and links. Keeping the spec, the tickets and every report local lets the loop rewrite them freely, and leaves GitHub with what people actually read: one issue that states the intent, and one PR that delivers it.

Why one issue, one branch, one PR

The issue's number is the intent's identity in git: the branch is [tag]/[N]-[intent-slug], every commit ends on (#N), and the PR closes #N. One task is one commit on that branch, so the history reads task by task, and a human reviews the whole intent once instead of a stack of small PRs.

The intent-slug

Every artifact of one intent carries the same intent-slug: the kebab-slug of the product title, or of the spec's goal, in lowercase ASCII with accents stripped. It names the intent's folder under .piv/, and every artifact opens with a header block — a short markdown list, one bold field per line — that carries it. Later steps read it from the artifact instead of re-deriving it — so a PRD written under user-auth/ never grows an authentication/ spec beside it.

House rules

  1. Nothing chains itself. Each skill ends by offering the next move; you run it.
  2. Each step reads the artifact before it. Reports are the input the next run works from, not paperwork.
  3. Skills stop rather than guess. A spec not reviewed, a task whose dependency isn't committed, a dirty tree with work that fits no group, gh not logged in — the run stops and asks.
  4. GitHub is written twice. piv-slice creates the issue and piv-open-pr opens the PR; every other step reads, or stays local.
  5. Review and fixes are separate runs. The reviewer writes findings and touches no code; the triage run decides what happens to each one, with you ruling on the split.
  6. Each task closes on a PASS. A fix run always hands back to a fresh review, which reads the deferrals so settled findings stay settled.
  7. One task at a time. Tasks run in the epic's order, never in parallel, each committed before the next starts.
  8. One language per intent. The PRD — or, with no PRD, the spec — is written in the language you interview in, and every later artifact follows it. Template headings and labels stay as the templates write them.
If a run stops and asks you something

That's the design, not a failure. Answer it and re-run — guessing is the one thing these skills won't do for you.

A full walkthrough

One intent with two tasks, start to merge. Each line is something you type, and the steps are grouped by the session they run in; the note beside each group says why, and which runs share a session explains the reasoning.

  1. piv-write-prd — interview, then a PRD lands at .piv/team-inbox/prd.md.

Its own session. The PRD is written to a file, and the next step reads it from there; nothing needs to stay in the conversation.

  1. piv-spec .piv/team-inbox/prd.md — it takes the PRD as input; the interview, then a spec lands at .piv/team-inbox/spec.md.

Fresh session. The PRD already holds the intent; the spec interview starts from the file, not from the PRD interview's context.

  1. piv-review-spec team-inbox — it finds an open PR that overlaps one requirement; you settle it, and the spec is reviewed.

Fresh session. The review must not share the interview's context.

  1. piv-slice team-inbox — two tickets and the epic; you approve the issue at the gate, and issue #123 opens with the spec as its body.

Fresh session. The slice only runs on what the review approved, and the spec and its review already hold everything it needs.

  1. piv-implement #123 — branch feat/123-team-inbox, task T-01, its tests, and tasks/T-01/T-01.report.md.

Fresh session, one per task. The heaviest step needs the whole window; in the planning session it would miss the ticket's gaps and bring back alternatives the interviews rejected.

  1. piv-review #123 — verdict CHANGES REQUESTED, 1 high and 3 medium in tasks/T-01/T-01.review.md.

Fresh session, always. In the implementation's session the review re-reads its own decisions and tends to confirm them.

  1. piv-fix .piv/team-inbox/tasks/T-01/T-01.review.md — you fix the high and one medium, defer two as D-01 and D-02; T-01.fixes.md records every ruling.

Fresh session. The run that raised the findings tends to defend them; the triage has to be free to rule against the review.

  1. piv-review #123 — it reads the deferrals, and the verdict is PASS.

Fresh session, always. In the fix's session the review would approve its own fix; only an independent PASS closes the loop.

  1. piv-commit #123 — one commit ending on (#123); T-01 turns [x] in the epic.

Fresh session. The commit body comes from the diff, not the reports. Then steps 5–9 run again for T-02.

  1. piv-commit #123 — the last task is committed.
  2. piv-open-pr #123 — the PR opens with Closes #123 and both deferrals in its body.

One session for both. Carrying a review-sized context costs more than starting over; the PR describes what the commits recorded, so nothing between them needs to stay independent.

  1. piv-review-pr #123 — every item of the spec is met: CONFORMS, and a human merges.

Fresh session. The audit must not share the context of the run that shipped what it audits.

Steps 6–8 repeat as many times as a task needs, each pass in fresh sessions. That cycle is the loop.

Which runs share a session

Every hand-off travels through an artifact — the spec, the epic, the tickets, the reports, the commits, the branch name — never through the conversation. A fresh session never loses anything the next step needs, so the choice weighs two things: whether the next run has to be independent, and what the session costs in tokens.

A shared session saves re-reading files, but every turn resends the whole session, and that cost grows with every tool call. A fresh session pays the re-read once and keeps later turns light. Sharing only pays when the next step would re-read almost everything the last one read and independence doesn't matter — which is why only the last commit and the PR share one (and a commit with a review that ended clean).

Combinations to avoid

spec + spec review: the interview judges itself. implement + review: self-approval. review + fix: the triage can't rule against the findings. fix + re-review: the loop closes without an independent PASS. fix or re-review + commit: a bloated session, and a commit body that retells the reports. planning + implement: the ticket's gaps go unseen and rejected alternatives come back. open PR + PR review: the audit inherits the story of what shipped.

Troubleshooting

The review keeps re-raising something I already decided to defer.

The deferral has to exist as a file under deferrals/ whose Origin names the task, not just a line in the conversation. piv-fix writes those files; piv-review reads them in its step 2. If the file isn't there, the finding legitimately comes back. A blocking finding comes back even when deferred: it closes only by fixing it, or by showing the problem isn't there.

The reviewer flagged something I changed on purpose.

Record it under Deviations from the ticket in the implementation report. That section is the reviewer's signal of intent. A test you changed is the exception: skipped, loosened, rewritten or deleted, it still blocks the review.

Can I skip the PRD?

Yes. The PRD is one input among others for piv-spec, and the spec is what the rest of the loop reads.

Can I run several tasks at once?

No. Tasks share one branch and are committed in the epic's order, so each review sees exactly one task's change against the last commit.

I edited the spec and now piv-slice stops.

Expected. The review approved one revision of the spec, by its hash; any edit after it needs piv-review-spec again.

The PR review says DIVERGES. Does piv-fix handle it?

No. piv-fix triages a task's review. A divergence in the PR is fixed by hand on the branch, planned as a new intent, or accepted at merge — your call.

Nothing moved after a skill finished.

Expected. Skills don't chain — read the next move it offered and run it yourself.
