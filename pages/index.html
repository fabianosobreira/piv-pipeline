Skills Manual

The PIV Loop

Plan → Implement → Verify. Eight skills that carry an idea from a blank page to a pull request a human can approve — one deliberate step at a time.

What the PIV loop is

PIV stands for plan → implement → verify. It is the shape this project's skills run work through.

  • Plan turns an idea into an intent, an architecture and a set of tickets.
  • Implement builds one ticket on its own branch and writes an implementation report.
  • Verify tries to prove the change wrong before it ships: a review writes findings, a triage run settles each one, and only then is the work committed and handed to a human.

Two properties hold the whole thing together. Every step reads the artifact the step before it wrote — the reports are not paperwork, they are the input. And every step is started by you, never by the step before it.

The core idea

Nothing chains itself. Each skill finishes by telling you the next move; you decide whether to run it. That is what keeps a bad plan from becoming a merged PR while you were away.

The chain at a glance

Plan
piv-create-prd or / and piv-create-architecture → piv-create-tickets
Implement
piv-implement-ticket
Verify
piv-review-changes → piv-fix-findings → piv-commit-changes → piv-create-pr

The loop closes on a PASS. piv-fix-findings always hands back to a fresh piv-review-changes. Only a PASS verdict earns a commit.

Read the arrows as "this is the next move offered", not as automation. The three verify skills before the PR are the gate; the PR itself is the handoff out of the loop, to a human who reviews, approves and merges.

Where do I start?

You rarely need all eight. Find the row that matches what you have in hand.

What you haveStart withWhy
A product idea, nothing written piv-create-prd You need the what and why pinned down before anyone argues about the how.
A PRD or an epic, and real technical uncertainty piv-create-architecture Decide the approach deliberately instead of letting tickets encode it by accident.
A clear intent with little technical risk piv-create-tickets A legitimate shortcut — just know you skipped the architecture step on purpose.
A ticket id ready to build piv-implement-ticket Tickets carry their own context, so the loop picks one up cold from its id alone.
Work built on a branch, not yet committed piv-review-changes This is the gate that decides whether the change earns a commit.
A review report with findings piv-fix-findings Findings are input, not a work order — you rule on each one.
A PASS verdict piv-commit-changes Atomic commits, then the PR.

Plan

The plan step produces three kinds of document, in increasing concreteness: intent (the PRD), decisions (the architecture doc) and units of work (the tickets). They are separate skills because they answer different questions, and mixing them is how a PRD quietly turns into a spec.

Plan · step 1

piv-create-prd

Interviews you to pin down the problem, why to build it, and a falsifiable hypothesis — then writes a product-level PRD. Intent only: what and why, never engineering decisions.

Input
[product idea] plus optional paths to research docs — user interviews, support-ticket themes, analytics, competitor teardowns. Blank starts with questions.
Output
docs/.plans/<intent-slug>.prd.md — problem statement, evidence, thesis, hypothesis, target user & JTBD, MVP, success metrics, non-goals, open questions.
How it runs
A clustered interview in five phases, each ending at a gate where it waits for you.
Guards
  • Evidence-or-TBD — every requirement traces to something you said or a doc showed; unknowns are written as "TBD — needs validation".
  • Intent-framed, not solution-prescriptive — if only one solution could fit the problem statement, it's a spec, not a PRD.
Next move
piv-create-architecture to decide the how, or piv-create-tickets directly when the work is technically boring — here or in a fresh session.
Use it when
  • You're starting something greenfield and no one has written down the problem yet.
  • You're scoping new work on an existing product — the research doc, decision plan or product docs that carry its context become the input.
  • Two people on the team would describe "the problem" differently.
Skip it when the intent already exists as a written epic or brief you trust.
Plan · step 2

piv-create-architecture

Weighs the options for how to build an intent, recommends a direction, and writes an architecture decision doc — approach, building blocks, data model, risks. It stops at the decision level; it is not an implementation plan.

Input
A PRD path, a brief, or a free-form idea, plus optional reference docs. References elsewhere (URL, page key, ticket id) are fetched from the source first.
Output
docs/.plans/<intent-slug>.architecture.md — problem & goals, approaches considered, recommended approach, key decisions, missing pieces, spikes & experiments, open questions.
How it runs
Grilling mode. It pushes back on your assumptions rather than transcribing them, and flags the one-way doors that deserve a spike before you commit.
Next move
piv-create-tickets <intent path> docs/.plans/<intent-slug>.architecture.md, here or in a fresh session — or go build a blocking spike first.
Use it when
  • There is more than one credible way to build the thing.
  • A decision is hard to reverse later — storage shape, a service boundary, a vendor.
  • The work touches an unfamiliar part of the system.
Skip it when the approach is obvious and the change is local. Say out loud that you skipped it.
Plan · step 3

piv-create-tickets

Decomposes an intent into agent-sized tickets with acceptance criteria and a dependency graph, then creates them on the project's tracker. This is also where the epic is born: it creates the epic and publishes the PRD and the architecture doc onto it before any ticket exists — the two plan skills before it write local files and know nothing about a tracker.

Input
One intent — PRD, epic, path, URL or ticket id — optionally with its architecture doc.
Output
The epic, with the PRD and the architecture doc published onto it — and real tickets under it, each with description, scope, per-ticket context, depends on, and acceptance criteria. Every ticket links back to the epic so the trace survives.
How it runs
Non-interactive through decomposition and dependency mapping, then one gate where you confirm the breakdown before anything is created.
Guard
With no architecture doc, it says so, keeps tickets outcome-shaped instead of implementation-shaped, and offers piv-create-architecture first when the technical uncertainty is real.
Next move
piv-implement-ticket <ticket-id>, in a session of its own, one per ticket — or start a wave of independent tickets in parallel, each in a session of its own.
Use it when an intent is settled and you need it sliced into units an agent can finish and prove. Each ticket carries its own context, so it can be picked up cold.

Implement

Implement

piv-implement-ticket

Builds one ticket task by task on its own branch, validating at every step, and writes an implementation report.

Input
[ticket-id | path-to-plan-document]. Blank and it asks which ticket.
Output
docs/.reports/<ticket-id>-report.md — summary, tasks completed, tests added, validation results, deviations from the ticket, issues encountered. Status is COMPLETE or PARTIAL.
How it runs
Resolve the ticket → work on a branch → read the ticket end to end → drift check → execute tasks in order → close the testing strategy → run the checks → final verification.
Next move
piv-review-changes, in a session of its own, handed the ticket id.
Why deviations matter. The reviewer reads this report. A deviation recorded here is an intentional decision the reviewer should not flag; the same deviation left unwritten comes back as a finding.

Verify

Verify is four skills and one rule: review and fixes are separate runs. The reviewer writes findings and touches no code. The triage run decides what happens to each finding, with you ruling on the split.

Verify · the gate

piv-review-changes

Reviews the finished change for bugs, security defects and standards violations, and writes a review report. It is a report, never an edit.

Input
[ticket id] — blank and it's taken from the branch name.
Output
docs/.reports/<ticket-id>-review.md — scope (every file read), findings grouped critical / high / medium / low, and the checks run. Each finding carries evidence, impact and a concrete fix.
Verdict
CHANGES REQUESTED when any critical or high finding survives. PASS otherwise — a PASS with medium and low findings is normal.
How it runs
Resolve the change → resolve prior deferrals → read the standards the change must meet → read every changed file end to end → build the case → run three filters that kill unproven findings.
Next move
PASS → piv-commit-changes, in a session of its own. CHANGES REQUESTED → piv-fix-findings, in a session of its own, handed this report's path.
Use it before committing anything, and again after every fix run. On a re-review it overwrites the previous report: it is the current state of the branch, and the rulings on old findings live in the tracker, not here.
Verify · triage

piv-fix-findings

Triages the review's findings, fixes the ones you choose one at a time with tests, defers and logs the rest onto the tracker, validates, and writes a fix report.

Input
[review report path] — blank and it uses the review written for this branch.
Output
docs/.reports/<ticket-id>-fixes.md — Fixed, Deferred (with issue refs), Needs a human look, Noise / won't-fix, and the checks run.
How it runs
Triage every finding into one of the four buckets → fix the fix now set one at a time, each with a test that proves it → validate the whole branch.
Next move
piv-review-changes again, in a session of its own, handed the ticket id.
Why the report exists. Triage is a human decision, and a decision that lives only in the conversation is gone by the next run. The fix report and the deferral issues are what tell the re-review that a finding was already settled — so settled findings stay settled.
Verify · commit

piv-commit-changes

Commits the finished work as atomic, conventionally-tagged commits — each one a coherent piece of work its subject line can name.

Input
[ticket id] — blank and it's taken from the branch name.
Output
Commits on the branch, plus a "What Changed" summary for someone skimming the git log. The run ends with a clean tree.
How it runs
Check where you are → inspect the tree → group the changes → commit each group → add a body when the subject isn't enough.
Next move
piv-create-pr, in this same session. The ticket id travels on the branch name, and that's where the next skill reads it from.
Use it once the review verdict is PASS. Usually this is a single commit; when the tree holds unrelated work it splits, and anything that fits no group stops the run and asks you.
Verify · handoff

piv-create-pr

Opens the pull request for the finished branch and hands the URL to a human reviewer.

Input
[base branch] — blank and it uses the project's base branch.
Output
A published branch and an open review request: summary, what changed, validation, notes for the reviewer, open issues, linked ticket. It reports the PR number, the URL and the base ← head branches.
How it runs
Resolve the base branch → check the branch is shippable → gather the body from the reports → publish → open the review request.
Next move
A human reviews, approves and merges. The agent's loop ends at the merge.
Portable by design. A pull request on GitHub, a merge request on GitLab, or marking a branch ready for review elsewhere — it uses whatever tooling the repo already uses.

Artifacts & where they live

Every step reads the artifact before it, so the paths matter. They are defined in docs/ISSUE-TRACKER.md.

docs/ISSUE-TRACKER.md is yours to customize — it is where a project declares which tracker it uses and what the artifact paths are, and the skills read that one filename and no other. docs/ ships worked examples to copy over it: ISSUE-TRACKER-gitlab.md, ISSUE-TRACKER-jira.md, and ISSUE-TRACKER-md.md for a project that keeps its tickets as local markdown files.

The plans are written locally and stay there; piv-create-tickets publishes a copy onto the epic — a comment on GitHub, an attachment on GitLab and Jira — so the decisions travel with the work instead of with the machine that wrote them.
The intent-slug

Every artifact of one intent carries the same intent-slug: the kebab-slug of the epic or product title. Every artifact opens with a header block — a short markdown list, one bold field per line — and the slug is its first field. Later steps read it from the artifact instead of re-deriving it — so a PRD written as user-auth.prd.md never grows an authentication.architecture.md beside it.

When the work has no ticket, the intent-slug takes the ticket id's place in the report filenames.

House rules

  1. Nothing chains itself. Each skill ends by offering the next move; you run it.
  2. Each step reads the artifact before it. Reports are the input the next run works from, not paperwork.
  3. Skills stop rather than guess. No tracker chosen, an ambiguous ticket id, a dirty tree with work that fits no group, a review report that doesn't exist — the run stops and asks.
  4. Review and fixes are separate runs. The reviewer writes findings and touches no code; the triage run decides what happens to each one, with you ruling on the split.
  5. The loop closes on a PASS. A fix run always hands back to a fresh review, which reads the deferral issues so settled findings stay settled.
If a run stops and asks you something

That's the design, not a failure. Answer it and re-run — guessing is the one thing these skills won't do for you.

A full walkthrough

One epic, start to merge. Each line is something you type, and the steps are grouped by the session they run in; the note beside each group says why, and which runs share a session explains the reasoning.

  1. piv-create-prd — interview, then a PRD lands at docs/.plans/team-inbox.prd.md.
  2. piv-create-architecture docs/.plans/team-inbox.prd.md — grilling, then a decision doc beside it.
  3. piv-create-tickets docs/.plans/team-inbox.prd.md docs/.plans/team-inbox.architecture.md — confirm the breakdown at the gate; tickets land on the tracker.

One session for all three. They collaborate rather than audit each other, and the interview's nuance carries over. Past half the window, break at a doc boundary — the docs already hold everything.

  1. piv-implement-ticket 123 — a branch, the tasks, the tests, and docs/.reports/123-report.md.

Fresh session, one per ticket. The heaviest step needs the whole window; in the planning session it would miss the ticket's gaps and bring back alternatives the interviews rejected.

  1. piv-review-changes 123 — verdict CHANGES REQUESTED, 1 high and 3 medium in docs/.reports/123-review.md.

Fresh session, always. In the implementation's session the review re-reads its own decisions and tends to confirm them.

  1. piv-fix-findings docs/.reports/123-review.md — you fix the high and one medium, defer two onto the tracker; docs/.reports/123-fixes.md records every ruling.

Fresh session. The run that raised the findings tends to defend them; the triage has to be free to rule against the review.

  1. piv-review-changes 123 — it reads the deferral issues, and the verdict is PASS.

Fresh session, always. In the fix's session the review would approve its own fix; only an independent PASS closes the loop.

  1. piv-commit-changes 123 — atomic commits, clean tree.
  2. piv-create-pr — the PR opens and the URL goes to a human.

One fresh session for both. Carrying a review-sized context costs more than starting over, and the commit body comes from the diff, not the reports. The PR describes what the commit recorded, so nothing between them needs to stay independent.

Steps 5–7 repeat as many times as the branch needs, each pass in fresh sessions. That cycle is the loop.

Which runs share a session

Every hand-off travels through an artifact — the PRD, the architecture doc, the tickets, the reports, the commits, the branch name — never through the conversation. A fresh session never loses anything the next step needs, so the choice weighs two things: whether the next run has to be independent, and what the session costs in tokens.

A shared session saves re-reading files, but every turn resends the whole session, and that cost grows with every tool call. A fresh session pays the re-read once and keeps later turns light. Sharing only pays when the next step would re-read almost everything the last one read and independence doesn't matter — which is why only the planning steps, and the commit with the PR, share one.

Combinations to avoid

implement + review: self-approval. review + fix: the triage can't rule against the findings. fix + re-review: the loop closes without an independent PASS. fix or re-review + commit: a bloated session, and a commit body that retells the reports. planning + implement: the ticket's gaps go unseen and rejected alternatives come back.

Troubleshooting

The review keeps re-raising something I already decided to defer.

The deferral has to exist as a tracker issue, not just a line in the conversation. piv-fix-findings opens those issues; piv-review-changes reads them in its step 2. If the issue isn't there, the finding legitimately comes back.

The reviewer flagged something I changed on purpose.

Record it under Deviations from the ticket in the implementation report. That section is the reviewer's signal of intent.

Can I skip the PRD or the architecture doc?

Yes, and both skills will say so out loud rather than pretend otherwise. Skipping the architecture doc on work with real technical uncertainty is the expensive one — the tickets end up encoding decisions nobody made.

Can I run several tickets at once?

Yes. piv-create-tickets maps dependencies in step 4 precisely so you can see which tickets form an independent wave.

Nothing moved after a skill finished.

Expected. Skills don't chain — read the next move it offered and run it yourself.
